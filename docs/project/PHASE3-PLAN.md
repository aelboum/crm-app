## 1. Scope

**In Phase 3:**
- contacts and companies: create, view, edit, archive, restore, and
  permanent delete;
- a contact's link to one company;
- tags;
- custom fields (definitions and values);
- notes;
- an activity timeline of record changes and notes;
- search, filtering, sorting and pagination;
- assigned owner;
- CSV import and export.

**Not in Phase 3; shown as unavailable in the UI:**
- tasks, opportunities, appointments and conversations (Phases 4–6);
- lead score (no defined model);
- saved views;
- merging duplicates (§8, deferred);
- the bulk actions "Add to automation" and "Add tag" on many records
  (the latter is a later increment);
- the workspace directory and member names (G1/G5; `PHASE2-PLAN.md`
  §6.4–6.5).

**Design differences, deliberate:**
- The prototype's stage "Patient" is a dental term and is excluded
  (P2-E). Default stages are Lead, Prospect, Customer and Inactive [R].
- The prototype links contacts to companies by name. Here the link is by
  ID (P2-E).
- The prototype has no delete, archive or merge controls; archive,
  restore and delete are added (§6).
- Companies get a full record page and an edit dialog, which the
  prototype lacks.

## 3. Data model

All tables live in schema `crm_app` and are tenant-owned. Every table has
`tenant_id uuid NOT NULL REFERENCES core.tenants(id)` and is covered by
RLS, the runtime-role grants, the schema guard (`tests/support.py`
`PRODUCT_TABLES`, `PURGE_COVERED_TABLES`) and the purge participant.

### 3.1 Conventions [R]
- **Primary keys:** `id uuid` generated by the application, plus a
  composite unique key `(tenant_id, id)`.
- **Foreign keys between product tables:** always composite,
  `(tenant_id, x_id) → (tenant_id, id)`. The database then makes a
  cross-workspace reference impossible, even with RLS bypassed.
- **Timestamps:** `created_at` and `updated_at` (`timestamptz`);
  `created_by_user_id` and `updated_by_user_id` hold SaaS-OS user IDs,
  with no foreign key into Core tables.
- **Concurrency:** `version integer NOT NULL DEFAULT 1` for optimistic
  locking (§6.3).
- **Archiving:** `archived_at timestamptz NULL`. Archived records are
  hidden from default lists and can be restored.
- **Text limits** in the database as `CHECK`s, mirrored by API
  validation: names 200, email 320, phone 32, URL 2048, note 10,000
  characters.
- **Indexes:** every index on a tenant table starts with `tenant_id`.

### 3.2 Tables

**`company`**
- `name` (required, trimmed)
- `domain` (optional; lower-case host with no scheme or `www.`)
- `website`
- `phone` (E.164 when it can be parsed)
- `industry` (free text in Phase 3) [A]
- `city`
- `country_code` (ISO 3166-1 alpha-2)
- `owner_user_id` (nullable)
- `custom_fields jsonb NOT NULL DEFAULT '{}'`
- standard columns (§3.1)
- partial unique index `(tenant_id, domain) WHERE archived_at IS NULL AND
  domain IS NOT NULL`, which drives the duplicate rule (§8)

**`contact`**
- `first_name` (required)
- `last_name`
- `email` (lower-cased)
- `phone` (E.164 when it can be parsed)
- `job_title`
- `city`
- `lifecycle_stage` (§3.3)
- `source` (§3.3)
- `company_id`: composite FK to `company`, `ON DELETE SET NULL` on
  `company_id` only
- `owner_user_id`
- `custom_fields jsonb`
- `import_id`, `import_row`: nullable, unique together per tenant (§9.2)
- standard columns
- `CHECK (email IS NOT NULL OR phone IS NOT NULL)`, as in the design's
  rule "email or phone is required"
- partial unique index `(tenant_id, email) WHERE archived_at IS NULL AND
  email IS NOT NULL`

**`tag`**
- `name` (unique per tenant, case-insensitively)
- `color` (one of a fixed palette)
- standard columns

**`contact_tag`, `company_tag`**
- `(tenant_id, contact_id | company_id, tag_id)` as the primary key,
  with composite FKs and `ON DELETE CASCADE`

**`custom_field_definition`**
- `entity` (`contact` or `company`)
- `key` (machine name, unique per tenant and entity)
- `label`
- `field_type`: `text`, `number`, `date`, `boolean` or `select`
- `options` (`jsonb`, for `select`)
- `position`
- `archived_at`

Values live in the record's `custom_fields` as `{key: value}`. They are
validated on every write against the active definitions; unknown keys are
rejected. [R] JSON is chosen over an entity-attribute-value table: reads
are one row, filtering on one custom field uses a GIN index, and
definitions stay the source of truth.

**`activity`**
- `kind`: `note`, or a system event (`created`, `updated`, `archived`,
  `restored`, `company_linked`, `imported`)
- `contact_id` or `company_id`: exactly one is set (`CHECK`); composite
  FKs with `ON DELETE CASCADE`
- `body` (notes only; ≤ 10,000 characters)
- `changes jsonb` (system events: names of the changed fields only, never
  their values)
- `actor_user_id`
- `occurred_at`

**`import_job` and `import_row`:** see §9.

### 3.3 Lifecycle stages and sources [A]
P2-E makes stages configurable per workspace. Phase 3 proposes a fixed
default set (Lead, Prospect, Customer, Inactive) stored as text with a
`CHECK`. A configuration table would follow in Phase 4 alongside
pipelines. Sources are a fixed list (Manual, Import, Form, Referral,
Other); Form becomes real in Phase 7. **Owner to confirm** that a fixed
set is acceptable for the MVP.

### 3.4 Owner of a record [R]
`owner_user_id` must belong to an active member of the workspace when it
is set; this is checked with SaaS-OS `get_membership` on write. If the
member is later suspended or removed, the value stays and the UI shows
"former member". There is no foreign key into Core.

## 4. Tenant isolation [R]

1. **One path for data access.** Every query runs inside
   `tenant_session_scope(context.tenant_id)`. The workspace comes from
   `require_permission`'s `RequestContext`, never from the path value or
   the request body (as the Phase 2 routes already do).
2. **Row-level security.** Each table gets `tenant_rls_statements` in its
   migration, plus `GRANT SELECT, INSERT, UPDATE, DELETE` to the runtime
   role, and nothing more (no `TRUNCATE`, schema `CREATE` or default
   privileges).
3. **Composite foreign keys** stop cross-workspace links at the database
   level.
4. **No client-supplied `tenant_id`.** Request schemas don't contain it;
   unknown fields are rejected (`extra="forbid"`), which also blocks mass
   assignment of `owner_user_id`, `version`, `archived_at` and similar.
5. **Not found everywhere.** A record ID from another workspace returns
   the same 404 as an unknown ID.
6. **Jobs.** The tenant comes from `TenantJobContext.tenant_id`, never
   from the payload data. Work runs in `tenant_job_session`, so a closed
   workspace stops its jobs.
7. **Guards.** `test_tenant_table_guard.py` already fails when a tenant
   table lacks RLS, the right grants, or purge coverage. Phase 3 adds each
   table to `PRODUCT_TABLES` and `PURGE_COVERED_TABLES` together with its
   migration.

## 5. Purge participation (gate G1)

As specified in `PHASE2-PLAN.md` §9.4, using **only** the public API that
#87 adds:
- `crm_app/purge.py` registers one participant in `create_app()`, the
  worker and the operator command's `--setup`.
- **Deletion order:** `activity`, then `contact_tag`/`company_tag`, then
  `import_row`, `import_job`, `contact`, `company`, `tag`,
  `custom_field_definition`.
- It then re-reads every manifest table for the tenant and raises if any
  row remains, so the tenant stays in PURGING and an audit row records the
  failure.
- **Tests:**
  - purging a test tenant with data in every table leaves zero rows;
  - another tenant's rows are untouched;
  - a failing participant leaves the tenant in PURGING;
  - a re-run completes;
  - the guard lists every tenant table.
- **Operator rule unchanged:** never `--no-product-participants`.

**[U]** The exact registration function name, and whether participants
receive a session or the tenant ID, depend on #87's final API. §5 is
updated when it lands; no internal import is used meanwhile.

## 6. API

Routes are under `/v1/workspaces/{tenant_id}`. Each declares exactly one
`require_permission` policy (checked by `tests/unit/test_routes.py`).
Error bodies use `{"detail": {"code": ...}}` as in the Phase 2 routes.

### 6.1 Endpoints

| Method and path | Permission | Notes |
| --- | --- | --- |
| `GET /contacts` | `crm_app.contact:read` | List (§7) |
| `POST /contacts` | `crm_app.contact:create` | Accepts an `Idempotency-Key` (`run_idempotent`); 409 `duplicate_email` (§8) |
| `GET /contacts/{id}` | `crm_app.contact:read` | Includes company summary, tags and custom fields |
| `PATCH /contacts/{id}` | `crm_app.contact:update` | Partial update with `If-Match: <version>` |
| `POST /contacts/{id}/archive`, `/restore` | `crm_app.contact:update` [A] | Reversible |
| `DELETE /contacts/{id}` | `crm_app.contact:delete` | Permanent; also removes the contact's notes and activity (§11) |
| `PUT /contacts/{id}/tags` | `crm_app.contact:update` | Replaces the tag set |
| `GET /contacts/{id}/activity` | `crm_app.activity:read` | Cursor-paginated; all roles hold it |
| Same set for `/companies` | `crm_app.company:*` | `GET /companies/{id}/contacts` lists linked contacts |
| `POST /contacts/{id}/notes`, `POST /companies/{id}/notes` | `crm_app.activity:create` | Member and above |
| `PATCH /notes/{id}`, `DELETE /notes/{id}` | `crm_app.activity:update` / `crm_app.activity:delete` | Admins, or the note's author (§6.2) [A] |

| `GET /custom-fields`; `POST`, `PATCH`, archive | read: `crm_app.contact:read`; change: `crm_app.workspace:update` [A] | Definitions are configuration |
| `POST /imports`, `GET /imports/{id}`, `POST /imports/{id}/commit`, `POST /imports/{id}/cancel` | §9.5 [A] | |
| `GET /contacts/export.csv`, `GET /companies/export.csv` | `crm_app.crm_data:export` | Owner and Admin only (Q6); rate-limited and audited |

A route that needs a second check (the note-author exception) declares its
broader permission as the route policy and applies the narrower rule in the
service, as the Phase 2 Owner rules do.

### 6.2 Permission interpretation [A]
These map the approved matrix (Q6, `roles.py`) onto concrete actions; the
owner should confirm them:
- **Archive and restore are updates.** Members can archive and restore;
  only Owners and Admins can delete permanently (Q6: "Only Owner and
  Admin can delete contacts, companies…").
- **Notes are activities.** Members create notes (`activity:create`).
  Editing or deleting needs `activity:update`/`delete` (Admin), with one
  exception: the author may edit or delete their own note. That route is
  then declared with `activity:create` and the service checks "author or
  holds `activity:update`/`delete`". **Owner to confirm.**
- **Tags and custom-field definitions are workspace configuration.**
  Changing them needs `crm_app.workspace:update` (Owner, Admin).
  Assigning existing tags to a record is a record update.
- **Import has no permission yet** (§9.5).

### 6.3 Validation and concurrency [R]
- Pydantic request models with `extra="forbid"`, length limits and
  trimming.
- **Email:** syntax check only; no DNS lookups.
- **Phone:** stored as entered, plus an E.164 form when it parses.
  Adding a phone library is a dependency decision [A]; until then, a
  conservative normaliser.
- **Domain and website:** URL parsing with only `http` and `https`
  allowed; the domain is derived from the website when absent.
- **Custom fields:** validated against the active definitions.
- **Updates require `If-Match: <version>`.** A mismatch returns 409
  `stale_version` with the current version, and the UI offers to reload.
  This keeps two editors from silently overwriting each other.

## 7. Lists: pagination, search, filters, sorting [R]

- **Keyset pagination** with an opaque cursor: base64 of the sort value
  and `id`. It is HMAC-signed with an application key, so a client cannot
  craft cursors. **[U]** The key comes from the SaaS-OS secrets provider;
  the name is to be added to settings.
  - `limit` defaults to 50 and is at most 200.
  - The response is `{items, next_cursor, approximate_total}`. An exact
    total is computed only when the filtered set is at most 10,000 rows;
    otherwise the UI says "10,000+". This matches the design's "N of M"
    within a bound.
- **Search (`q`)** is case-insensitive over contact name, email, phone
  and company name, and over company name, domain and city.
  - **Phase 3a:** prefix match using `lower()` expression indexes; no
    extension.
  - **Phase 3b [A]:** substring and fuzzy search with `pg_trgm` GIN
    indexes. It is a trusted extension, but enabling it is a database
    change that needs approval.
  - Search input is length-limited to 100 characters and always bound as
    a parameter.
- **Filters**, repeatable within a field (OR), combined across fields
  (AND):
  - `lifecycle_stage`, `owner_user_id` (or `me`), `tag_id`, `company_id`;
  - `archived=false|true|all` (default `false`);
  - `created_after` / `created_before`;
  - companies: `industry`, `city`.
- **Sorting** is allow-listed: name, created_at, updated_at,
  lifecycle_stage and owner, each ascending or descending. Unknown
  values return 422, never interpolated SQL.
- **Indexes:** `(tenant_id, archived_at, lower(last_name), lower(first_name),
  id)`, `(tenant_id, updated_at, id)`, `(tenant_id, owner_user_id)`,
  `(tenant_id, company_id)`, and GIN on `custom_fields` only when custom
  field filters are added.
- **Performance target:** the list returns in under 300 ms at the 95th
  percentile, measured with 100,000 contacts in one workspace on CI-class
  hardware.

## 8. Duplicates [R]

1. **Create or edit:** an active contact with the same email (or an
   active company with the same domain) returns 409 `duplicate_email` /
   `duplicate_domain` with the existing record's ID. The UI offers "Open
   existing". The partial unique indexes enforce this under concurrency.
2. **Archived records** don't block. Restoring one that would collide
   returns 409.
3. **Import** has a per-run policy: `skip` (default), `update_existing`
   (match on email or domain) or `create_anyway`, which is refused
   wherever the unique index would be violated.
4. **Merge** is deferred to a later increment. It needs a field-by-field
   choice, moving notes and tags, and an audit trail; the design shows
   none of this.

## 9. Import [R]

No SaaS-OS file storage exists [V], so no uploaded file is ever stored.

### 9.1 Flow
1. **Upload and preview** (`POST /imports`):
   - accepts multipart CSV, UTF-8 (with or without a BOM) or Windows-1252
     detected;
   - limits: ≤ 5 MB and ≤ 10,000 data rows;
   - parsed in the request with Python's `csv` module (no new
     dependency); the column mapping is supplied or proposed from
     headers;
   - every row is validated with the same validators as the API, then
     normalised;
   - only normalised values are written to `import_row` (status `valid`
     or `invalid`, with error codes and field names); the raw file is
     discarded;
   - returns counts, the first 50 errors (row number, field, code, never
     the cell value) and a preview of duplicates under the chosen policy;
   - the job's status is `previewed`.
2. **Commit** (`POST /imports/{id}/commit`) enqueues the product job
   `crm_app.import_commit`. The worker processes valid rows in batches of
   500, each in its own `tenant_job_session` transaction.
3. **Progress** (`GET /imports/{id}`): status (`previewed`, `queued`,
   `running`, `completed`, `completed_with_errors`, `failed`,
   `cancelled`), counts created / updated / skipped / failed, and error
   rows as CSV (row number, field, code).
4. **Cancel** (`POST /imports/{id}/cancel`): stops after the current
   batch; committed rows stay, and nothing is rolled back across batches.

### 9.2 Partial failure and retries
- Delivery is at-least-once [V]. Each batch is idempotent: a created
  contact carries `(import_id, import_row)`, unique per tenant, so a
  re-run batch inserts nothing twice; updates compare `version`.
- The job stores a checkpoint (the last completed row) in `import_job`. A
  retry resumes from it.
- After 3 tries the job is dead-lettered; status becomes `failed`, and
  the counts show exactly what was committed. A "Resume" action enqueues
  the job again.
- One import per workspace at a time, enforced by an advisory lock.

### 9.3 Retention and privacy
- `import_row` holds personal data. It is deleted 7 days after the import
  finishes [A] by a product cron job, and it is covered by purge.
- No cell value appears in logs, audit metadata or error responses.

### 9.4 Security
- Size and row limits are enforced before parsing completes.
- Parsing is streamed.
- No formulas are evaluated.
- No URL in the file is fetched.
- The rate limit is 10 previews per user per hour (`enforce_rate_limit`).

### 9.5 Permission [A]
The catalogue has no import permission. Options:
- **(a) [R]** Add `crm_app.crm_data:import` (Owner, Admin) to the
  catalogue **before the first real workspace is provisioned**. No real
  workspace exists yet, so no migration of existing roles is needed, and
  gate G7 (#88) is not involved. Test workspaces in `crm_app_test` are
  recreated per run.
- **(b)** Require both `contact:create` and `contact:update`, which lets
  Members import.

Owner decision needed. (a) matches Q6's treatment of export as
administrative.

## 10. Export [R]

- `GET /contacts/export.csv` takes the same filters as the list; likewise
  for companies.
- The response is a synchronous stream; nothing is stored, because there
  is no file storage [V].
  - Bounded at 50,000 rows; above that, 413 `export_too_large` with a
    hint to narrow the filters. Asynchronous export waits on storage
    [U].
  - Columns are fixed, plus custom fields.
- **Spreadsheet formula injection:** any cell starting with `=`, `+`,
  `-`, `@`, a tab or a carriage return is prefixed with `'`.
- `Content-Disposition: attachment` and `Cache-Control: no-store`.
- **Audited** as `crm_app.contacts.exported`, with metadata of the row
  count and filter keys only (never values or personal data).
- **Rate-limited** to 10 exports per user per hour.
- **Permission:** `crm_app.crm_data:export` (Owner, Admin).

## 11. Privacy and retention [R]

- Contacts are third parties' personal data under the GDPR, and the EU is
  the market (K5).
- **Permanent delete** removes the contact, its notes, its activity, its
  tags and its `import_row` rows in one transaction. The audit entry
  keeps only the record ID and actor.
- **Archive** is not deletion; the UI says so.
- **Subject access:** a single contact's data, exported as JSON, is a
  later increment, because SaaS-OS has no export or erasure hooks [V/U].
- Purge covers every table (§5).

## 12. Audit [R]

All entries are written with `record_in_transaction` in the same
transaction as the change, as `caller=UserCaller(actor)`, or
`SystemCaller` for jobs.

| Action | When | Metadata (never personal data) |
| --- | --- | --- |
| `crm_app.contact.created` / `.updated` / `.archived` / `.restored` / `.deleted` | each change | changed field names; source (`api` or `import`) |
| same for `company` | | |
| `crm_app.contact.company_linked` | link changes | company ID |
| `crm_app.tag.*`, `crm_app.custom_field.*` | configuration changes | key, type |
| `crm_app.import.previewed` / `.committed` / `.completed` / `.failed` / `.cancelled` | import lifecycle | counts, duplicate policy |
| `crm_app.contacts.exported` / `crm_app.companies.exported` | export | row count, filter keys |

- **Not audited:** reads and searches, because of volume. Exports are
  audited because they move data out.
- Audit is distinct from the user-visible activity timeline: audit is for
  accountability (`crm_app.audit:read`), while activity is for sales
  context.
- **[U]** The `SystemCaller` authority to use for import jobs must be
  confirmed against SaaS-OS's documented system authorities before S7.

## 14. Tests

**Unit:**
- validators and normalisers (email, phone, domain, custom-field types);
- cursor encoding and signature rejection;
- sort and filter allow-lists;
- CSV parsing (encodings, BOM, quoted newlines, size and row limits);
- formula-injection escaping;
- duplicate policies;
- permission interpretation table (§6.2) against `ROLE_TEMPLATES`;
- route policies (every new route has exactly its intended permission).

**Integration (real PostgreSQL, `crm_app_test`):**
- CRUD for every entity, including `If-Match` conflicts;
- list paging correctness: no duplicates or gaps while rows are inserted
  between pages;
- search and every filter;
- duplicate 409s under two concurrent creates (barrier test, as in G-LOCK);
- import: preview, commit, the job processed in-process, resume after a
  simulated failure between batches with no duplicates, cancel, and
  retention clean-up;
- export: content, escaping, the bound, the audit row and the rate limit.

**Security and cross-tenant:**
- for every route, a member of workspace B using A's IDs gets 404 and
  nothing changes;
- RLS: as the runtime role, a raw `SELECT` with no tenant set returns 0
  rows, and with the wrong tenant set returns 0;
- a composite FK refuses a cross-tenant `company_id` even with RLS off
  (run as the migration role in the test);
- mass assignment of `tenant_id`, `owner_user_id`, `version` or
  `archived_at` is refused;
- every role against every route (the Q6 matrix);
- injection in `q`, `sort` and CSV cells;
- a job payload naming another tenant is ignored;
- purge leaves zero rows (G1);
- the schema guard covers every new table.

**Frontend (Vitest):**
- every state (loading, empty, error, denied, unavailable);
- forms and validation;
- conflict and duplicate dialogs;
- axe scans of the list, drawer, record and dialogs.

**Browser:** list to drawer to record to edit, with keyboard only, at
phone width, with contrast checks.

## 17. Acceptance criteria (Phase 3 exit, refining ROADMAP §8)

1. Contacts and companies persist in PostgreSQL with RLS on every table,
   and the guard proves it.
2. Every implemented control in the Contacts and Companies screens calls a
   real API. Every unimplemented one is labelled unavailable.
3. CRUD, archive, restore, delete, search, filters, sorting and cursor
   pagination work with 100,000 contacts within the §7 target.
4. The role matrix holds for every route, and a member of another
   workspace sees 404 for every ID.
5. Duplicates are handled as in §8, including under concurrency.
6. An import of 10,000 rows can fail and resume without duplicates.
   Export escapes formulas, is bounded, audited and rate-limited.
7. Purging a workspace leaves no product rows (G1 tests).
8. Unit, integration and frontend tests pass in CI; axe scans of the new
   screens have no violations; browser checks are recorded.
